一、项目定位与设计要点

一句话：把自然语言描述的作战问题，可靠地转换成"有全局约束、数字可追溯、冲突可仲裁"的结构化决策支持。

核心玩法是"总指挥 + 三军参谋"的角色分工——不是一个大模型包打天下。用户问"陆军多少人多少装备"，只派陆军参谋查库回答；用户给一个复杂作战背景，才由总指挥拆解任务、下发约束，海陆空三参谋并行拟案，最后由总指挥仲裁出决心方案。

与通用大模型的五点关键差异：

维度通用大模型本系统
数字靠"说"，会编全部查 SQLite，带来源，可审计
约束谁都能改条件只能总指挥下发，参谋不得越权
冲突三军需求打架无人裁共享资源冲突检测 → 协商 ≤3 轮 → 强制裁决
边界什么活都接领域外明确拒答（写周报、翻译一律不接）
轮次单轮一锤子多轮增量重规划：改一个条件只重算受影响的参谋

产出不是"一段回答"，而是可校验、可追溯、可复盘的结构化方案。

三、分期、资源与顺序

总原则：先底层、后前端。一期到四期全部是后端能力（图、状态、规则、数据、模型），前端页面框架放到最后一期——底层跑通之前不做界面，避免界面反复返工。

期内容判据
第一期（本轮） 真实兵力池（SQLite）＋ 接线上模型，跑通最小闭环 "陆军多少人"答得对、数字可追溯
第二期协商循环落盘 ＋ 完整硬规则执行三军争资源能自动检出并裁决
第三期多轮会话 ＋ 增量重规划改一个条件只重算受影响参谋
第四期本地部署大模型 ＋ 集成、韧性命令行下一轮完整会话可用；本地模型通过 T1–T12 回归
第五期MCP 外部服务 ＋ 前端页面框架 ＋ 其他补充页面可独立完成一轮会话，方案可直接阅读分享

模型路线（已定）：先接线上模型调试 → 链路与提示词稳定后 → 第四期再本地部署。好处：先用最强模型把"参谋能不能干好活"验证清楚，避免在模型能力和工程问题之间互相甩锅；本地部署后置，届时只做能力回归，不推翻设计。

需要的资源：① 线上 LLM API 账号（主力＋轻量双档，双档可省约 80% 辅助成本）；② 兵力池种子数据（3 份 JSON，我方出结构、业务方填数）；③ 第四期本地部署算力（待第二期后评估）；④ 第五期前端人力。

四、风险（如实说）

  1. 中途失控：不做最后一锤子买卖，分期累积验收，每期有独立判据。
  2. 语义层未验证：真模型下参谋方案质量未知，Mock 只证明了控制流正确——这正是"先接线上模型"要优先解决的事。
  3. 成本：单轮全链路最坏约 24 次主力调用（协商拉满时），最好 4 次。已设三道闸门（轮次 ≤3、只拉冲突方、震荡即退）。
  4. 本地部署的能力落差：换本地模型后方案质量可能下降。对策：复用同一套 T1–T12 用例做回归，不达标则调整本地模型规格或保留线上／本地混合模式。
  5. 前端长期缺席：一至四期只能用命令行与 trace 日志演示，观感弱。对策：第四期起同步输出结构化 trace 与方案文件，作为没有界面时的验收与讲解依据。

五、四项已定决策

#事项决策带来的影响
1范围与顺序 先做最小可用（第一期） 本期只做真实兵力池＋线上模型＋最小闭环；协商、多轮、本地部署、MCP、前端逐期顺延
2模型路线 先接线上模型调试，通过后本地部署 先用强模型验证语义层可行性；本地部署排在第四期，只需做能力回归，不推翻设计
3验收口径 链路跑通即可 以三类典型链路（拒答／单域快通道／全链路协商）＋ 四类故障注入的行为断言为准，不设精确率／性能量化指标；若后续要求"兵力问答零差错"，需另开工期
4工程顺序 先做底层框架，跑通后再搭前端页面 图／状态／规则／数据／模型先打通并以 trace 验收；前端放第五期，避免底层未定就被界面绑死、反复返工
